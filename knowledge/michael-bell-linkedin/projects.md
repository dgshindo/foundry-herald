# Michael Bell --- Projects

Use real project decisions, problems, implementations, failures,
lessons, and milestones as LinkedIn material. Never invent features or
present unfinished work as complete.

## Foundry Herald

A multi-brand content generation and Facebook publishing application
that evolved from a smaller content utility.

Demonstrated capabilities include: - database-driven
brands/destinations - separate brand knowledge and content history -
multiple content types - draft/edit/save/approve/reject workflow -
repetition avoidance - publishing guardrails and state transitions -
destination-aware Facebook publishing - distinct House Dainislaav and
Sonic Foundry identities

Useful engineering stories include separating core behavior from brand
identity, brand-scoped memory, replacing hard-coded destinations with
configuration, debugging repository field selection, debugging approved
→ publishing → published state transitions, removing remaining
single-brand assumptions, and deliberately postponing image generation
because cost/scope did not justify it.

Do not repeatedly retell the whole origin story. Prefer one concrete
lesson per post.

## The Sonic Foundry

A PHP/MySQL software platform centered on guided music creation and
progressive creative decisions rather than one giant input prompt.
Relevant engineering topics include database-backed context, API
integrations, OAuth, deployment, music-generation API experiments,
workflow design, and translating creative processes into software.

Do not claim experimental features are production-ready.

## The Forge --- After Effects Production Application

A tool that began as automation for repetitive After Effects work and
grew toward a production/branding application. Relevant concepts include
project creation, brand profiles, multiple aspect ratios, audio/SRT
import, lyric treatment, branding assets, smoke/embers, end screens,
project save/open, rendering, and reusable scripted workflows.

Useful themes: automating repetitive work, designing around a real
workflow, maintaining scope, and recognizing when a script launcher
becomes an application.

## Project Content Rule

A strong project post should answer at least one question: What problem
was being solved? What assumption was wrong? What decision mattered?
What failed? What changed? What tradeoff was made? What did the
implementation teach? What would be done differently?
